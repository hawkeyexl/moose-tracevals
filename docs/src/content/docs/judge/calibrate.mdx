**Scope:** measuring whether the tool agrees with you, and turning the knobs once you know. It
assumes [How the judge decides](/moose-tracevals/judge/) — you cannot tune a zone threshold before
you know what consensus is.

The tool can always tell you what it decided. Calibration is how you find out whether it was
**right**, and there is a command for it:

```bash
moose-tracevals calibrate <traces...> --labels tracevals/labels.yaml
```

It runs the corpus, joins the results against the answers you wrote down, and counts the three
things that matter — [false passes, false fails, and review volume](#the-three-numbers).

## Write down what you decided

Ground truth lives in a **sidecar file**, not in the artifacts. A label belongs to a corpus and to
the person who reviewed it: two teams calibrating the same skill against different sessions hold
different answers, and neither belongs in the `SKILL.md`.

```yaml title="tracevals/labels.yaml"
version: 1
labels:
  - trace: ../../traces/claude-session.jsonl
    artifact: fix-bug
    eval: forbidden-tool
    expected: pass
    note: The only in-window Bash call was a read-only `git status`.

  - trace: ../../traces/claude-session.jsonl
    artifact: reviewer
    type: agent
    eval: reviewer-is-read-only
    expected: pass
```

| Field | Required | Meaning |
|---|---|---|
| `trace` | yes | Path to the trace, resolved **against this file's own directory** — not your working directory, so a committed labels file means the same thing from anywhere. |
| `artifact` | yes | The name the report shows: a skill name, a `subagent_type`, or a project-rules filename such as `CLAUDE.md`. |
| `type` | no | `skill`, `agent`, or `project-rules`. Needed only to disambiguate a name two artifact kinds share. |
| `eval` | yes | The eval's `id`. |
| `expected` | yes | `pass`, `fail`, or `needs-review`. |
| `note` | no | Why you decided that. It travels into the disagreement report, where it is the thing that makes a disagreement actionable. |

`expected: needs-review` is a real answer, not a hedge. Label the two or three sessions you found
genuinely ambiguous and the report will tell you whether the review band caught them.

<Aside type="caution" title="Label by `id`, and give your evals one">
An eval declared with the [string shorthand](/moose-tracevals/reference/evals-schema/) has no `id`,
so it gets a **positional** one — `eval-1`, `eval-2`. Reordering the block silently re-points every
label at a different assertion. Declaring an explicit `id` costs one line and removes the problem.
</Aside>

### What the file refuses

All four refusals are the same refusal: a labels file that quietly means less than it says.

| Refused | Why |
|---|---|
| An unknown member — `reason:` where you meant `note:` | The schema is closed, so a typo would silently drop the label |
| An empty `labels` list | It measures nothing while looking like a measurement |
| Two labels for one `(trace, artifact, eval)` | Whichever won would silently decide the number |
| A `trace` outside the corpus you are running | Checked before anything is judged, so a misspelling costs no inference |

A label that survives all four and still matches no eval result is **exit 2** as well, reported
after the run with the ids that trace actually produced. It cannot be a warning: a typo'd id
contributes to no count, so the report would come out looking like a cleaner corpus than it is.

## The three numbers

Point the command at the corpus. Every example on this page runs offline against this
repository's own fixtures.

{/* test {"testId":"calibrate","description":"calibrate reports the three numbers, sweeps for free, and gates only when asked."} */}
{/* step {"description":"Calibration measures the corpus and exits 0 even though it disagrees.","runShell":{"command":"moose-tracevals calibrate test/fixtures/traces/claude-session.jsonl test/fixtures/traces/claude-session-sidecar.jsonl --project test/fixtures/project --labels test/fixtures/project/tracevals/labels.yaml --provider mock --no-cache","exitCodes":[0],"stdio":"false passes"}} */}

```bash
moose-tracevals calibrate test/fixtures/traces/claude-session.jsonl \
  test/fixtures/traces/claude-session-sidecar.jsonl \
  --project test/fixtures/project \
  --labels test/fixtures/project/tracevals/labels.yaml \
  --provider mock
```

```
moose-tracevals calibrate — 2 trace(s), 10 label(s)
runs 3 · autoPass 0.8 · autoFail 0.8 · labels test/fixtures/project/tracevals/labels.yaml

Agreement 5/8 (62.5%)
     1  false passes   labelled fail, judged pass — the expensive error
     1  false fails    labelled pass, judged fail — erodes trust fastest
     1  needs-review   across the whole corpus — the review volume
     0  deferred       labelled pass or fail, routed to a human instead
     1  missed reviews labelled ambiguous, decided anyway
     0  errors         the eval could not be graded at all
     2  unscored       labelled, but the eval never armed
```

**False passes** are the expensive error: something you would have failed came back green.
**False fails** erode trust fastest — the tool cried wolf, and the next person believes it less.
**Review volume** is the operational cost of the band: too many and nobody reads them, too few and
the band is not doing its job. It counts `needs-review` across *every* eval in the corpus, labelled
or not, because "nobody reads them" is a question about volume rather than accuracy.

Three more rows exist because the grid of (what you said × what it said) is bigger than three cells,
and collapsing it hides the interesting parts:

| Row | What happened |
|---|---|
| `deferred` | You said pass or fail; the tool routed to a human. It declined rather than being wrong — the behaviour zones exist to produce. |
| `missed reviews` | You said ambiguous; the tool decided anyway. This is the row to watch while raising `autoPass`. |
| `unscored` | The eval never armed — an unmet [conditional trigger](/moose-tracevals/declare/coverage/), an empty window, a `metadata.eval-skip`. |

<Aside title="Unscored labels stay out of the denominator">
`Agreement 5/8` above comes from ten labels minus two that produced no evidence. A check that never
armed has not been satisfied, so folding it in would let a corpus nobody exercised report perfect
agreement — the same reason a [batch pass rate](/moose-tracevals/reference/report-and-exit-codes/#batch-runs)
excludes skips. An eval that **errored** is a disagreement, never an agreement, by the same rule
that makes [an errored run count against consensus](/moose-tracevals/judge/#from-votes-to-consensus).
</Aside>

## Which eval disagreed

A count with no route back to an assertion is a number nobody can act on, so every disagreement is
listed with the arithmetic behind it and the note you wrote:

```
Disagreements
  FALSE-FAIL     claude-session.jsonl  fix-bug › forbidden-tool (tool-usage)
                 expected pass, got fail
                 note: The only in-window Bash call was a read-only `git status`.
  FALSE-PASS     claude-session.jsonl  AGENTS.md › eval-1 (ai)
                 expected fail, got pass · 3p/0f/0?/0e over 3 run(s), confidence 0.95
                 note: The change touched four packages; that is not small and reviewable.
  MISSED-REVIEW  claude-session.jsonl  fix-bug › eval-5 (ai)
                 expected needs-review, got pass · 3p/0f/0?/0e over 3 run(s), confidence 0.95
                 note: One file got its test first, the other did not.

Unscored (no evidence either way)
  SKIPPED        claude-session-sidecar.jsonl  CLAUDE.md › source-edits-use-the-fix-bug-skill
                 trigger not met (whole session): no file matching "src/**" was accessed
```

Read the two judged rows before touching a knob. Both are unanimous at confidence `0.95`, so **no
zone threshold below `0.95` will move them** — the assertions are the problem, not the band. The
first row is not a judge problem at all: `forbidden-tool` is a deterministic `tool-usage` eval that
is simply too blunt. Deterministic and `human`-graded evals are calibrated exactly like judged ones,
and a blunt option produces a false fail as readily as a hesitant model does.

That is the diagnosis this page used to ask you to make by eye:

- **Reviews clustered just under the threshold, unanimous.** The threshold is too high for your
  model. Lower it and watch `false passes`.
- **Reviews with split votes.** The *assertion* is ambiguous, and no threshold will fix it. Go
  sharpen the eval.

## Sweep the knobs for free

`--sweep` re-scores the same corpus at every setting in the grid and reports what each one would
have produced.

```bash
moose-tracevals calibrate <traces...> --labels tracevals/labels.yaml --sweep
```


One row moves, and it is the whole answer: at `autoPass: 0.95` the false pass disappears and review
volume goes from 1 to 4. That is the trade stated in numbers instead of adjectives — you buy the
removal of one wrong verdict with three more deferrals — and you can make the call without running
anything again.

**One axis at a time**, every other knob held at its configured value, because that is what "move
one knob and recount" has always meant. The full cross-product of the default grid is 108 rows and
answers a question nobody asked. The grid itself lives in
[`calibrate.sweep`](/moose-tracevals/reference/configuration/#calibrate).

### Why it is free

Verdicts are cached per-run, and a judged eval's report carries **every run** the ensemble made —
the votes, the confidences, the errors. Zone thresholds were never part of the
[cache key](#what-invalidates-a-cached-verdict): they are applied *after* consensus, not sent to the
model. So a different `autoPass` is arithmetic over verdicts already on disk.

`ensembleRuns` **is** in the key, so the sweep handles it differently: the corpus is judged once at
the **largest** ensemble the grid asks for, and each smaller cell is scored from the first *k* of
those runs.

<Aside type="caution" title="Two consequences, and neither is hidden">
A swept `ensembleRuns` row is a **sub-sample** of the ensemble that was drawn, not a fresh *k*-run
ensemble. At temperature 0 the runs are independent samples of one prompt, so it is an honest
estimate — but it is an estimate.

And a sweep's **first** run costs `max(calibrate.sweep.ensembleRuns)` runs per judged eval instead
of your configured count: 5 rather than 3 with the defaults. Every sweep after it is free, because
the cache key depends on the grid rather than on the cell. Narrow the grid if that first run
matters.
</Aside>

## The knobs themselves

All live under `tracevals.judge` in `moose.config.yaml`; see the
[configuration reference](/moose-tracevals/reference/configuration/) for types and defaults.

| Knob | Default | Moving it up | Moving it down |
|---|---|---|---|
| `ensembleRuns` | `3` | Costs proportionally more. Makes auto-resolution *harder* — every run must agree. More reviews, fewer confident mistakes. | Cheaper and more decisive, with a higher chance a single unlucky sample decides an eval. |
| `zones.autoPass` | `0.8` | Fewer auto-passes, more reviews. | Converts reviews into passes. Buys throughput with accuracy. |
| `zones.autoFail` | `0.8` | Fewer auto-fails, more reviews. | Converts reviews into fails. |
| `temperature` | `0` | Adds noise. Warns once per process. | Already at the floor. |

Two things are worth internalising before you turn anything:

**More runs make the gate stricter, not looser.** Auto-resolution requires unanimity, so a fourth
run is a fourth chance for one dissent to send the eval to review. If reviews are drowning you,
raising `ensembleRuns` will make it worse.

**Zones are a floor on mean confidence, not a vote threshold.** Unanimity is required regardless.
Lowering `autoPass` to `0.6` does not let a 2–1 split pass; it only lets a *unanimous but hesitant*
ensemble through.

<Aside type="caution" title="Leave temperature at 0">
Nonzero temperature adds noise to verdicts, which is the opposite of what an ensemble is for — you
want independent samples of the same judgement, not varied ones. moose-tracevals warns once per process
if you set it above zero. `--sweep` does not vary it for the same reason.
</Aside>

## Measurement, not a gate

`calibrate` exits **0 even when it disagrees with you**. The first honest calibration of a real
corpus finds disagreement — that is the point of running it — and a command that fails on its own
findings is one people stop running, or start running with `|| true`.

Two things do turn it red:

<Steps>

1. **A threshold you asked for, and missed.** What counts as too many false passes is your decision,
   so state it:

   {/* step {"description":"A threshold turns a measurement into a gate.","runShell":{"command":"moose-tracevals calibrate test/fixtures/traces/claude-session.jsonl test/fixtures/traces/claude-session-sidecar.jsonl --project test/fixtures/project --labels test/fixtures/project/tracevals/labels.yaml --provider mock --max-false-pass 0","exitCodes":[1],"stdio":"exceeded"}} */}

   ```bash
   moose-tracevals calibrate <traces...> --labels tracevals/labels.yaml --max-false-pass 0
   ```

   ```
   Thresholds
     falsePass: 1 of at most 0 — exceeded

   Exit 1: a threshold was exceeded, or a trace in the corpus could not be evaluated.
   ```

   `--max-false-fail` and `--max-review` work the same way, and all three have
   [config equivalents](/moose-tracevals/reference/configuration/#calibrate).

2. **A trace in the corpus that could not be evaluated.** The measurement is then incomplete, and an
   incomplete number presented as a clean one is worse than no number.

</Steps>

{/* test end */}

Everything else is exit `2` and operational — a missing or invalid labels file, a label naming a
trace outside the corpus, a label matching no eval. See the
[CLI reference](/moose-tracevals/reference/cli/#calibrate).

## Cap what it can spend

```yaml title="moose.config.yaml"
tracevals:
  judge:
    maxCostUsd: 2.50
```

Checked **before each judged eval**, and the budget spans the whole invocation — every trace in a
batch or a calibration corpus is charged against one total, not one each. Once it is spent, the
remaining evals are reported as `skipped` with the reason naming the budget, rather than being
dropped silently:

```
SKIP   CLAUDE.md › adheres-to-artifact (implicit)
       judge cost budget exhausted ($2.5)
```

Because it is checked per eval and evaluated in order, a budget stops the run *somewhere in the
middle* — the evals that got skipped are an artifact of ordering, not importance. Treat a
budget-exhausted run as incomplete rather than as a result. In a calibration run those evals become
`unscored` rows, so an exhausted budget can never inflate agreement.

<Aside type="caution" title="A budget is only as good as the price table">
Cost is computed from a built-in per-model price table. **A model the table does not recognise is
costed at zero**, which silently disables `maxCostUsd` entirely — the budget never trips because
spend never accumulates. If you run a model that is not in the table, set its price explicitly:

```yaml
tracevals:
  provider:
    openai:
      model: my-self-hosted-model
      pricing:
        inputPerMTok: 0.15
        outputPerMTok: 0.60
```
</Aside>

## What invalidates a cached verdict

Verdicts are cached under `judge.cacheDir` (default `.moose-tracevals/cache`), keyed on seven things:

1. provider
2. model
3. **prompt version**
4. ensemble run count
5. temperature
6. a hash of the rendered trace
7. a hash of the eval plan — the assertion, evidence, examples, and the artifact's full content

Change any one and you get a fresh judgement. Change none and you get an instant replay, which is
what makes a sweep free: **zone thresholds are not in the key**, because they are applied after
consensus rather than sent to the model.

<Aside type="caution" title="The silent one: a stale cache after a prompt change">
Prompt version is in the key precisely so a prompt revision cannot replay verdicts produced by the
old prompt. That protection only works if the version is bumped. If you fork this project and edit
the judge prompts, bump `PROMPT_VERSION` in `src/judge/prompt.ts` in the same change — otherwise
every cached eval silently keeps answering with a prompt that no longer exists.

To rule the cache out while debugging, run with `--no-cache`. Note that `--no-cache` and `--sweep`
together still work, but the sweep then re-scores verdicts produced fresh in that run.
</Aside>

Note that the artifact's **content** is in the key, so editing a `SKILL.md` re-judges every eval on
it. That is intended: the instruction changed, so the previous verdict is about a different
question.
