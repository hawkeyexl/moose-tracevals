**Scope:** the *denominator* — every instruction file a session referenced, including the ones that
could not be found. Deciding what to check on a resolved artifact is
[Declare what to check](/moose-tracevals/declare/).

Every report ends with a coverage section, and it answers a question the eval list cannot:
**what did you not check?**

```
Artifact coverage
  ✓ skill: fix-bug           /work/demo-project/.claude/skills/fix-bug/SKILL.md
  ○ agent: Explore           built-in agent (no definition file)
  ○ skill: my-plugin:foo     not found (3 location(s) tried)
  ✓ slash-command: ship-it   /work/demo-project/.claude/commands/ship-it.md
  ○ slash-command: model     built-in slash command, or not installed here (no definition file)
  ✓ agent: doc-writer [not offered]  /work/demo-project/.claude/agents/doc-writer.md
  ✓ project-rules: project rules

Availability
  5 skill(s) offered, 2 used, 3 never used
  3 agent(s) offered, 2 used, 1 never used
  pass --report-unused-artifacts to list them
```

## The six states

| What you see | Meaning | What to do |
|---|---|---|
| `✓` with a path | Resolved and evaluated. | Nothing. |
| `✓` with no path | Resolved to **several** files. Only project rules do this. | Nothing — see [below](#project-rules-resolve-as-one-entry). |
| `○ built-in agent (no definition file)` | A built-in agent, which has no file anywhere. | Nothing. Expected. |
| `○ built-in slash command, or not installed here` | A `/name` with no command file and no skill file anywhere. | Usually nothing — see [below](#slash-commands-are-one-of-three-things). |
| `○ not found (<n> location(s) tried)` | The trace referenced it; no file matched. | [Close the gap](#fix-an-unresolved-reference). |
| Absent from the list entirely | The session never referenced it. | Nothing. |

An unresolved reference is **not** a failing eval. It becomes a coverage row plus a warning, so a
missing plugin never crashes a run or turns a build red on its own. That is deliberate: a skill file
you do not have is not an adherence violation. It does mean that artifact went unchecked, which is
exactly what the table is telling you.

## Offered, used, and never on the menu

The list above answers *what did the session reference*. The **Availability** block answers a
different question — *what could it have referenced* — and keeps three states apart:

| State | Meaning | What to do |
|---|---|---|
| **offered and used** | On the roster, and the session used it. | Nothing. |
| **offered and not used** | On the roster, never invoked. | A judgement call. Read the description and decide whether it should have fired. |
| **not offered** | The session referenced it, but it was never on the roster. | Fix the **configuration**. This is not an adherence failure. |

That third state is the one that wastes an afternoon. A skill or agent someone expected but which
was never on the menu produces evals that fail — or, worse, skip — for a reason that has nothing to
do with the session's behaviour. It is labelled inline:

```
  ✓ agent: doc-writer [not offered]  /work/demo-project/.claude/agents/doc-writer.md
```

The definition file exists on disk and resolved fine; it was simply never offered to that session.
Look at plugin installation, agent scope, and whether the name was renamed after the session ran.

**None of this is an eval outcome.** Availability never appears in the summary counts and never moves
the exit code — it is an observation about the session's configuration, not a verdict on its
behaviour.

### Listing what went unused

Offered-and-unused artifacts are **counted, not listed** by default: a real roster runs to a couple
of hundred skills and would bury the evals above it. To see them with the descriptions that Claude
Code itself uses to decide whether to invoke:

```bash
npx moose-tracevals run <trace> --deterministic-only --report-unused-artifacts
```

```
  · skill: deep-research [offered, unused] offered, never used — Fan-out web searches, fetch sources, verify claims, synthesise a cited report.
  · skill: bare-listing [offered, unused] offered, never used
  · agent: researcher [offered, unused] offered, never used — Gathers background before a change is designed. (Tools: Read, WebFetch)
```

A row like `bare-listing` above shows nothing after the dash because the roster carried no
description for it — Claude Code truncates its listing text, and past that cap it names skills alone.
Absent means *not recorded*, never "has none".

An unused row is marked `·` rather than `○`, and reports `n/a` under **Resolved** in markdown, because
nothing was ever looked for on disk. Saying "not found" would be a claim about a search that never ran.

<Aside title="Where the roster comes from">
Not a filesystem scan — the transcript itself. Claude Code records what it offered as structured
attachment records, so the evidence travels inside the trace and the answer is the same on any
machine. Full detail in [the traces reference](/moose-tracevals/reference/traces/#the-availability-roster).

A trace with **no** roster reports it as unknown rather than as zero. Older sessions and
`claude-stream` transcripts carry no listing records at all.
</Aside>

To act on an unused artifact rather than just look at it, hang a
[conditionally-triggered eval](/moose-tracevals/reference/graders/#conditional-triggers) on
`CLAUDE.md` — the one artifact that resolves for every session.

## How an artifact is resolved

Resolution is **deterministic** — trace content plus filesystem lookup, with no model involved. The
trace records which skills were invoked and which agents were spawned; moose-tracevals then looks for the
matching files in a fixed order and records every location it tried.

### Skills

For a plain reference like `fix-bug`, in order:

1. `<project>/skills/fix-bug/SKILL.md`
2. `<project>/src/skills/fix-bug/SKILL.md`
3. `<project>/.claude/skills/fix-bug/SKILL.md`
4. `<home>/.claude/skills/fix-bug/SKILL.md`
5. `<home>/.claude/plugins/**/skills/fix-bug/SKILL.md` — searched recursively, because plugin store
   layouts nest differently

A `plugin:skill` reference **skips steps 1–4** and goes straight to the plugin store, matching on
the short name with the plugin name required somewhere in the path.

### Agents

1. `<project>/.claude/agents/<name>.md`
2. `<project>/agents/<name>.md`
3. `<home>/.claude/agents/<name>.md`

A `plugin:agent` reference looks up the short name.

**Built-in agents are never resolved**, because they have no definition file: `general-purpose`,
`claude`, `Explore`, `Plan`, `statusline-setup`, and `fork`. They appear as `○` with a note, and
that is the finished state rather than a problem to fix.

### Slash commands are one of three things

When a session records `/name`, that reference can be any of three different things, and only the
filesystem can say which. Resolution tries them in order:

1. `<project>/.claude/commands/<name>.md`
2. `<home>/.claude/commands/<name>.md`
3. the same two directories searched recursively — a subdirectory under `commands/` **organizes**
   without renaming, so `commands/release/tag.md` is still `/tag`
4. failing all of those, the [skill order](#skills) above, because a skill can be invoked by typing
   its slash form
5. failing that too, it is a **built-in** — one of Claude Code's own commands (`/model`, `/compact`,
   `/clear`), which has no file anywhere by design

A `plugin:command` reference **skips steps 1–3** and goes straight to
`<home>/.claude/plugins/**/commands/<name>.md`, matching on the short name with the plugin name
required somewhere in the path — the same rule plugin skills follow.

Step 5 is a note, not a warning, because a built-in is the expected outcome rather than a defect.
The note says `built-in slash command, or not installed here` and the row still carries every
location tried, so a command that genuinely *is* missing on this machine is still diagnosable from
the `tried` list. Nothing here is checked against the availability roster: the transcript records no
roster of slash commands, so calling one `not offered` would be a claim about evidence that was
never collected.

### Project rules

Every directory from the session's working directory **up to the project root** (the git root by
default, capped at 32 levels), then `<project-root>/.claude/`. In each one it checks `CLAUDE.md`,
`AGENTS.md`, and `GEMINI.md`.

**All matches are collected**, not just the first. A repository with a root `CLAUDE.md` and a nested
`AGENTS.md` gets both evaluated.

<Aside title="`--project` when the workspace has moved">
Resolution starts from the session's recorded `cwd`. If that directory no longer exists — the trace
came from another machine, or the checkout was moved — point it somewhere else:

```bash
npx moose-tracevals run <trace> --project ./my-repo
```
</Aside>

## Fix an unresolved reference

The coverage entry records **every location it tried**, which is usually the whole diagnosis. In
JSON output that is the `tried` array:

```bash
npx moose-tracevals run <trace> --deterministic-only --format json
```

```jsonc
{
  "ref": "my-plugin:foo",
  "kind": "skill",
  "resolved": false,
  "tried": ["/home/you/.claude/plugins/**/skills/foo/SKILL.md"]
}
```

Read the list and the cause is usually one of:

- **The plugin is not installed** on the machine running moose-tracevals. Install it, or run with
  `MOOSE_TRACEVALS_HOME` pointed at a directory that has it.
- **The artifact moved** relative to the project — a skill relocated from `skills/` to
  `.claude/skills/` resolves fine, but one moved outside those roots will not.
- **The project root is wrong**, so the walk started somewhere unexpected. Set `--project`.
- **It was renamed** after the session ran. The trace holds the old name; nothing on disk matches.

Each unresolved reference also emits a warning next to the table:

```
Warnings
  ! skill "my-plugin:foo" was invoked but no SKILL.md was found (1 location(s) tried)
```

## Staleness

Evals are read from the artifact **as it is now**. The session followed it **as it was then**. Edit
a `SKILL.md` after a session and you are grading that session against instructions it never saw — a
`fail` on a rule that did not exist yet, or a `pass` on one whose wording has since changed.

Every resolved artifact is compared against the session's end time, and one that is newer is marked:

```
Artifact coverage
  ✓ skill: fix-bug /work/demo/.claude/skills/fix-bug/SKILL.md ⚠ modified after the session ended (2026-08-29T17:14:19.176Z)

Warnings
  ! 1 artifact(s) were modified after the session ended (fix-bug) — their evals may not be the instructions this session followed. mtime is a heuristic, not content identity.
```

In JSON, the entry carries `stale: true` and `modifiedAt`.

<Aside type="caution" title="It is a heuristic, and a noisy one in CI">
The comparison is **mtime**, which is not content identity. In particular, `git clone` and
`git checkout` rewrite every mtime to *now* — so **a CI job that checks out the repository and then
evaluates an older trace flags every artifact**. That is the heuristic working as designed, not a
bug, and it is exactly why this is a warning.

It **never becomes an eval outcome and never changes the exit code**. The artifact still resolves,
its evals still run, and its verdicts are unaffected. All that changes is what the report says about
how much to trust them
([ADR 01021](https://github.com/hawkeyexl/moose-tracevals/blob/main/adrs/01021-warn-when-an-artifact-changed-after-the-session.md)).
</Aside>

A trace with no recorded end time is never flagged: there is nothing to compare against, and
inferring one would manufacture a warning out of no evidence.

When a flagged row matters, the fix is to evaluate against the artifact as it was — check out the
commit the session ran on and re-run with `--project` pointed at that working tree.
An unresolved **slash command** is the one exception: it gets its coverage row and its `tried` list
but no warning, because the common case — a built-in — is not a gap to close.

## Project rules resolve as one entry

Project rules appear as a single row named `project rules` with **no path**, because the entry
covers however many files matched. Its `tried` array holds every location checked, and each matched
file is evaluated as its own artifact — which is why `CLAUDE.md` and `AGENTS.md` show up separately
in the eval list above.

If none matched, the row reads `○ project-rules: project rules  no CLAUDE.md or AGENTS.md found`.

## What the implicit eval covers

A resolved artifact that declares **no** evals is still evaluated, through one judged eval named
`adheres-to-artifact`. So a `✓` row always means the artifact was checked, even when you have
authored nothing for it.

Silence in the eval list therefore means the artifact was never *referenced* by the session, not
that it was skipped.

## Skip an artifact deliberately

To take an artifact out of evaluation without deleting its evals:

```yaml
metadata:
  evals:
    skip: true
```

It is then reported as `skipped` with the reason `artifact skipped via metadata.eval-skip`, which
keeps it visible rather than silently absent. Full field reference in the
[evals schema](/moose-tracevals/reference/evals-schema/).

## Duplicate references collapse

A skill invoked six times produces **one** coverage row and one set of evals. Deduplication is by
reference name for coverage, and by resolved path for artifacts — so two references that resolve to
the same file are evaluated once.
